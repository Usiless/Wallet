## New repair-round finding

**P2 — following-installment edits reject payments on installments they should preserve.** `lib/features/payments/domain/pending_payment_service.dart:436-443`.

Concrete source trace: create a bank plan of300 in three installments of100. Pay80 on installment2, leaving its residual20; leave installments1 and3 unpaid. Edit installment1 to50 with `following:true`. The target list includes installment2 because its residual is positive. The loop saves installment1, then compares the proposed50 against installment2's already-paid80 and throws before reaching `if (q.paidMinor > 0) continue`. The transaction rolls back, so neither unpaid installment is editable through this action. The old reviewed source skipped that already-paid installment before validating the replacement amount, preserving installment2 and updating installments1/3.

This is reachable from the existing UI: an unpaid first installment exposes “Editar pendiente” (`payments_screen.dart:338`) and “Esta cuota y las siguientes” (`:419`), passed as `following` at `:451`. A later installment may legitimately have been partly paid before the first one. The approved rule is that future pending edits preserve earlier payments; rejecting because of an untouched installment's payment is an unintended restriction introduced by this fix.

**Smallest correction:** exclude the paid installments the operation intentionally preserves before applying the proposed-amount guard, or move the existing `paidMinor > 0` skip before that guard. Retain the carry lower bound on every obligation actually mutated. Add a regression with this three-installment setup: first/third become50, second stays amount100/paid80/remaining20, and its ledger movement stays unchanged. The existing deleted-payment/carry bound regression must remain green. No runtime reproduction was run in this review, per assignment; the failure follows directly from the changed guard order.
