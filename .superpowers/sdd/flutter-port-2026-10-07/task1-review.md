## Confirmed findings

1. **P1 — installment category allocation can create negative money.** `lib/features/payments/domain/pending_payment_service.dart:216-223`. With total 10, two installments and category totals A3/B3/C3/D1, first installment is [1,1,1,2], second [2,2,2,-1]. The last category absorbs all other rounding error without respecting its remaining allocation. On payment, remainingSplits drops D-1 and rescales A/B/C to five, losing the promised per-category totals; the backup validator also rejects the app's own negative split. Smallest fix: allocate each installment against nonnegative remaining category capacities, distributing integer remainders across categories with capacity, while keeping exact row totals and final column totals. Add this four-category fixture and assert every split nonnegative and each category's final paid total exact.

2. **P1 — edit can reduce an obligation below already transferred debt.** `lib/features/payments/domain/pending_payment_service.dart:414-429`. Create two 100 installments, pay 40 from first and carry60 to second, delete the40 payment, then edit first amount to50. Hydration makes paidMinor0, so edit accepts50 while carriedMinor remains60. remainingMinor becomes -10, the original debt is hidden from positive-pending reports, and its own backup rejects it as overpaid. Smallest fix: validate amountMinor >= paidMinor + carriedMinor transactionally before mutating each selected obligation; preserve transferred categories when scaling the remaining editable allocation. Add exact deletion/carry/edit regression, including valid edit equality and backup roundtrip.

3. **P2 — changing only schedule leaves prepared future obligations intact.** `lib/features/templates/manual_template_service.dart:81-86` plus scheduler horizon `lib/features/templates/scheduled_template_service.dart:91-94`. The comparison deliberately removes schedule and only economic/name differences enter future propagation. After current and following month have been prepared, moving nextDate or changing monthly to yearly retains both old future obligations; next processing can add new-date obligations on top. Smallest fix: explicitly reconcile unconfirmed prepared occurrences on user schedule edits, preserving actual paid links and historical deduplication; distinguish the scheduler's own nextDate advancement from a user calendar edit. Test monthly date change, monthly/yearly switch and repeated processDue. Do not apply reconciliation to historical actual movements.

4. **P2 — backup accepts orphaned transferred debt.** `lib/core/backup/backup_service.dart:330-366`. Start with a valid unpaid categorized100 obligation. Set carriedMinor20 and carriedSplits[A20], without carries or carriedTo. Validation accepts: paid+carry<=100, category sum20, and both reference checks are optional. Runtime now shows80 pending and the transferred20 exists nowhere. Uncategorized obligations also bypass the carried-total check. Smallest fix: require a complete nonempty transfer history and valid targets whenever carriedMinor>0, with history sums and category sums matching cumulative carry; require zero/absent fields to agree when no carry. Validate each history split/reference rather than merely its amount and target. Add malformed-snapshot rejection plus genuine categorized/uncategorized carry roundtrips. If historical persisted carry representation needs compatibility, explicitly normalize a valid legacy carriedTo record; do not silently permit missing targets.
